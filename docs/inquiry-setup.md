# Хүсэлтийн panel, имэйл мэдэгдлийн тохиргоо

Каталогийн “Үнийн санал авах” товч нь барааны нэрийг маягтад оруулна. Маягтаас илгээсэн хүсэлт Supabase PostgreSQL санд хадгалагдаж, Resend-ээр танай Gmail эсвэл өөр имэйлд мэдэгдэл илгээгдэнэ. `/admin` дээр хүсэлтүүдийг үзэж, Шинэ / Холбогдсон / Дууссан төлөвөөр удирдана.

## 1. Supabase

1. Supabase project үүсгээд SQL Editor дотор [inquiries.sql](../supabase/inquiries.sql)-ийг ажиллуулна. Энэ SQL нь хүсэлтүүд, серверүүдийн дунд хуваалцах хүсэлтийн хязгаарлалтыг үүсгэнэ.
2. Authentication → Users дээр panel-д орох хэрэглэгчийг имэйл, нууц үгтэйгээр үүсгэж, имэйлийг нь баталгаажуулна. Нээлттэй бүртгэл шаардлагагүй тул Allow new users to sign up тохиргоог унтраана.
3. Project URL, legacy `anon`, legacy `service_role` key-г `.env.local` эсвэл hosting-ийн environment variables-д оруулна. `service_role` key-г браузер болон `NEXT_PUBLIC_*` хувьсагчид хийж болохгүй.
4. Эрхтэй хэрэглэгчдийн имэйлийг `ADMIN_EMAILS`-д таслалаар тусгаарлаж оруулна. Нэвтэрсэн бүх хэрэглэгч админ болохгүй; энэ жагсаалтад байгаа, баталгаажсан хэрэглэгч л эрхтэй.

Supabase Auth нь нууц үгийг шалгана. Token нь HTTP-only, SameSite=Strict cookie-д хадгалагдана. Production дээр cookie нь HTTPS шаарддаг. Panel-ийн session нэг цаг хүртэл үргэлжилнэ; дуусвал дахин нэвтэрнэ. Клиентэд хүсэлтийн хүснэгтийн эрх олгоогүй, сервер админы эрхийг хүсэлт бүрд шалгана.

## 2. Имэйл мэдэгдэл

Хүсэлт хүлээн авах хаяг: `Pagmasuren@interpro.mn`. Энэ хаягийг `.env.example` болон локал тохиргоонд оруулсан. Hosting дээр мөн `INQUIRY_EMAIL_TO=Pagmasuren@interpro.mn` гэж тохируулна.

1. Resend account дээр илгээх домэйнээ баталгаажуулж, API key үүсгэнэ.
2. `RESEND_API_KEY`, `INQUIRY_EMAIL_FROM` (жишээ нь `INTERPRO <requests@your-domain.mn>`), `INQUIRY_EMAIL_TO` (танай Gmail хаяг, эсвэл таслалаар тусгаарласан хаягууд)-г тохируулна.
3. `NEXT_PUBLIC_SITE_URL`-д энэ deployment-ийн бодит HTTPS хаягийг тавина. Локал орчинд `http://localhost:3000`. Preview deployment ашиглавал түүний URL-ийг тусад нь тохируулна.

Мэдэгдэлд нэр, утас, имэйл, бараа/үйлчилгээ, эвентийн огноо, оролцогчдын тоо, асуулт болон panel-ийн холбоос багтана. Хэрэглэгч имэйлээ оруулсан бол Reply хийхэд тэр хаяг руу хариулна.

Имэйл үйлчилгээ түр тасарсан ч хүсэлт хадгалагдана. Panel дээр “Имэйл мэдэгдэл илгээгдээгүй” хүсэлтийг нээгээд “Дахин илгээх”-ийг дарна. “Илгээгдсэн” гэдэг нь Resend хүсэлтийг хүлээн авсан гэсэн утгатай; хүлээн авагчийн inbox-д хүрсэн эсэхийг Resend logs-оос шалгана. Автомат retry cron энэ хувилбарт байхгүй.

Resend-ийн idempotency key 24 цаг хадгалагдана. Имэйл явсан ч мэдээллийн сангийн status update тасарсан тохиолдолд энэ хугацаанд дахин илгээх нь давхар имэйлээс хамгаална. 24 цагаас хойш pending/failed хүсэлтийг дахин илгээхээс өмнө Resend logs-ийг шалгаарай.

## 3. Ажиллуулах, шалгах

`.env.example`-ийг `.env.local` болгон хуулж, дээрх утгуудыг бөглөөд `npm run dev` ажиллуулна. Нууц утгуудыг git-д commit хийхгүй.

1. Бараанаас үнийн саналын хүсэлт илгээж, амжилтын мэдэгдэл харуулж байгааг шалгана.
2. `/admin` дээр нэвтэрч, нэр, сонгосон бараа болон асуултыг зөв хадгалсныг шалгана.
3. Gmail-д мэдэгдэл ирснийг шалгана.
4. Хүсэлтийн төлөв өөрчилж, хуудсаа шинэчлэхэд төлөв хадгалагдсаныг шалгана.
5. Гараад `/api/admin/inquiries` нь 401 буцааж байгааг шалгана.

`npm test` нь validation, эрхийн шалгалт, давхар хүсэлт, имэйл тасарсан үеийн хадгалалт, retry-г upstream үйлчилгээний mock ашиглан шалгана. Бодит Supabase, Resend тохиргоотой end-to-end шалгалтыг deployment-ийн өмнө дээрх дарааллаар хийнэ.

Vercel болон өөр сервер дээр ижил managed database ашиглана. Өөрийн reverse proxy ашиглавал `X-Forwarded-For`-г зөвхөн proxy өөрөө тохируулдаг болгоно. Одоогийн public endpoint IP бүрээс 10 минутад 5 шинэ хүсэлт хүлээн авна; илүү хатуу bot хамгаалалт шаардлагатай үед CAPTCHA нэмнэ.

Үйлчилгээний түлхүүрүүдгүй үед хүсэлт хадгалсан мэт амжилт харуулахгүй, тохиргоо хийгдэж байгааг мэдээлнэ. Имэйл тохиргоо дутуу боловч database ажиллаж байвал хүсэлт хадгалагдаж, notification нь retry хийх төлөвтэй үлдэнэ.
